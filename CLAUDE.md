# Project: MyCastle

## Komunikacja
Wszystkie komunikaty, odpowiedzi i wyjaśnienia pisz **po polsku** (z pełną poprawnością ortograficzną i polskimi znakami). Terminy techniczne i identyfikatory z kodu zostają w oryginale.

## Overview
pnpm monorepo zarządzający danymi PIM (osoby, taski, projekty, eventy, shopping, IoT/Minis devices, CAD). Współdzielone pakiety w `packages/`, aplikacje w `app/`.

> **Uwaga:** ten plik trzyma tylko architekturę wysokopoziomową i konwencje. Po szczegóły API (klasy, propsy, pola modeli) używaj `grep`/`Read` na kodzie źródłowym — kod jest źródłem prawdy.

## Architecture

### Shared packages (`packages/`)

Zbudowane przez `tsup` (dual ESM+CJS o ile nie zaznaczono inaczej). Wszystkie pod scope `@mhersztowski/`.

- **core** — współdzielone modele (Person/Task/Project/Event/Shopping/Minis*/User/Iot*/SmartDisplay/Auth), nody (z UI state + `copyBaseStateTo()`), MQTT topic registry (Zod-based, single source of truth), RPC registry (Zod), VFS abstraction (MemoryFS/CompositeFS/GitHubFS/WritableGitHubFS/BrowserFS/NodeFS/RemoteFS/**MqttFS**), automate models, datasource (IDataSource + MemoryDataSource), MJD (Meta JSON Definition), IoT device-side building blocks (IotDeviceExtension/VfsExtension/Client — framework-agnostic).
- **core/browser/** — kod ładowany wprost w przeglądarce. Starsze bundle to vanilla JS (no TS, no build, eksport przez `globalThis`), nowsze moduły są w TS i bundluje je Vite hosta (`server/api.ts` — fasada komend backendu dla skryptów w Drive, `aura/aura.ts`, `api/api.ts`). Trzy bundle vanilla: `mycastle/` (PIM nodes + ApiClient REST), `qt/` (QObject+Signal + widgety Qt na canvasie + przykłady), `scene3d/` (Vec3/Box3/Geometry/MeshBuilder). Używane w Plugin Script, Lit, automatyzacjach, HTML `<script type="module">`.
- **core-backend** (ESM-only) — `FileSystem` (in-memory cache, atomic writes, fileChanged events), `HttpUploadServer` (rozszerzalna baza dla MycastleHttpServer), `MqttServer` (Aedes wrapper z auth+routing), `JwtService` (TTL 7 dni)/`PasswordService` (bcrypt)/`ApiKeyService` (prefix `minis_`, SHA-256), `checkAuth()` middleware, `DataSource`, `RpcRouter`, interfejsy `IAutomateService`/`IDataSource`.
  - **`src/projects/`** — serwisy budowania projektów **przeniesione z `app/mycastle-backend/src/modules/`**: `arduino` (`ArduinoService`, `ArduinoWasmBuilder`), `upython` (`MicroPythonService`), `pygame` (`PygameService`), `picosdk` (`PicoSdkService`). Backend importuje je z `@mhersztowski/core-backend`, nie z własnych modułów.
    - `ArduinoWasmBuilder` montuje mock Arduino z repo (`docker/arduino-mock/` → `/arduino-mock:ro`, ścieżkę nadpisuje `ARDUINO_MOCK_DIR`), więc zmiana mocka **nie wymaga przebudowy obrazu**; kopia `COPY` w `Dockerfile.cli` jest fallbackiem dla deploymentu. Rozjazd obrazu z repo objawiał się wcześniej dopiero błędem linkera „symbol exported via --export not found".
  - **`src/server/`** (`ServerApi`/`ServerLogic`) — protokół komend backendu (MQTT `/server/cmd` + HTTP `POST /api/server/cmd`). Poza plikami i gitem obsługuje: **e-mail** (`email_list`/`email_read`/`email_send`), **skrzynkę wiadomości** (`mail_send`/`mail_inbox`/`mail_outbox`, model `Mail`), **archiwa ZIP** (`zip_pack`/`zip_unpack`/`zip_update`/`zip_delete`) i **budowanie projektów** (`project_arduino_build`/`project_picosdk_build` + `*_get_output`). Konfiguracja przez `ServerLogicOptions` + `SecretsProvider`; kontrakt opisany w `docs/backend_api.md`.
- **server-logic** (ESM-only) — warstwa „server logic" uruchamiana in-process z backendem. `IotServer` (LogService + ActivityService + ConsoleService + CronService + ClientRegistry), MQTT control plane (`server/inbox`·`outbox`, `{user}/...`, `{user}/{device}-{clientType}/{id}/...`), `MqttList<T>`, `Envelope`, `IMqttTransport`. Konwencja: **inbox=do encji, outbox=od encji**.
- **devtools** (ESM-only) — toolkit **kod ⇄ UML**. Parsery: TS Compiler API + web-tree-sitter (Python/C/C++). `CodeModel` (IR z deterministycznym djb2 id), `UmlSyncService` (scan dir → generate/update UML z layoutem, diff→git-like history, codegen TS/Python/C++), `GitRepoService` (CLI git wrapper, obsługa `.repo.json`).
- **web-client** — React klient backendu. `MqttClient` (WS, request-response, **size-aware: MQTT <2MB / HTTP większe**, `setUserBasePath()` tenant isolation, path normalization), `FilesystemService` + Context/Provider, `configureUrls()` (auto-detect z `window.location`), `TypeDocViewer`, MJD edytory React. **Uwaga:** Monaco/VFS UI/pluginy przeniesione do `texteditor`.
- **texteditor** — Monaco multi-editor workspace. **Pisząc wtyczkę, przeczytaj najpierw `packages/texteditor/docs/plugins.md`** — pułapki, których nie widać w typach (polecenia mają prefiks `pluginId:` z dwukropkiem, eksplorator porównuje ścieżki VFS a nie identyfikatory zakładek, drzewo ładuje gałęzie leniwie, motyw MUI jest jasny w ciemnym chromie, brak punktu rozszerzenia dla panelu dolnego). Peer: React/MUI/Monaco/XTerm/@xyflow/react/blockly). `TextEditorWorkspace` (reusable wrapper z opcjonalnym AI agent + terminal + project actions), `SubpathFS` (prefix VFS), `VfsExplorer`/`VfsMountManager`/`VfsCommitDialog`, `Project` base + 8 typów projektów (Arduino/NodeJs/PicoSdk/Pygame/UPython/Notes/Python/Editor), builtin pluginy (TypeScript/Python/C++ IntelliSense, Markdown LSP/Preview, MJD editor, VisualMinisLib ReactFlow), `ArduinoBoardConfigDialog`.
- **web-cpp** — browser-side C++/WASM runtime simulator dla Emscripten MODULARIZE+ASYNCIFY. `CppWasmRuntime` dialog: build (SSE), run, pin visualizer (14 digital+6 analog), serial monitor, **panel DISPLAY** (framebuffer RGBA8888 z `minis_canvas_present()`). Renderer w `displayRenderer.ts`: **WebGL2** (tekstura aktualizowana `texSubImage2D` wprost z widoku na stertę WASM, skalowanie NEAREST na GPU) z fallbackiem na canvas 2D; mock publikuje `HEAPU8.subarray` (bez kopii) — odbiorca musi zużyć dane synchronicznie. Zdarzenia wskaźnika wracają do szkicu przez `minis_canvas_push_event`.
- **core-scene3d** — 3D scene core (Three.js + @react-three/fiber). `SceneNode`/`SceneGraph`, węzły (MeshNode/LightNode/CameraNode/GroupNode/**UiRootNode**+**UiWidgetNode**), `RenderEngine`/`RenderLoop`, `SimpleViewer` (R3F + OrbitControls + TransformControls gizmo, `autoFit`, camera presets standard/blender/maya/cad), I/O (GLTF/OBJ/STL), **`GLTFImporter`** (glTF/GLB jako **poddrzewo sceny**: hierarchia, przekształcenia, materiały PBR z metalicznością i chropowatością, zliczenie węzłów i ostrzeżenia; `parseGLTFBuffer` zostaje dla pojedynczej bryły, ale brał z pliku tylko pierwszą siatkę — dlatego edytor używa importera. `.gltf` bez sąsiedniego `.bin` daje ostrzeżenie zamiast pustej sceny. **Tekstura osadzona w `.glb`** jest przepisywana na `data:` (`textureData.ts`) — obraz z bufora pliku istnieje tylko w pamięci i nie ma ścieżki ani adresu, którym dałoby się go wskazać; bez tego model wchodził biały bez śladu. `BufferGeometryData.uvs` przenosi współrzędne tekstury — renderer je wcześniej wyrzucał, więc mapa nie miała się na czym położyć. Wariant **embedded** `.gltf` (bufor i obraz jako `data:`) działa tak samo jak `.glb`. `MaterialDescriptor.maps` niesie pozostałe mapy PBR (normal/roughness/metalness/emissive/ao) — mapy techniczne dostają `NoColorSpace`, bo niosą liczby, nie barwy; korekcja gamma rozjaśniłaby je i zepsuła oświetlenie. Waga tekstur liczona **łącznie** na materiał, bo pięć map naraz robi ze sceny plik nie do otwarcia. **`MaterialDescriptor.textureSettings` niesie sposób nakładania** (`wrapS`/`wrapT`/`repeat`/`offset`/`flipY`, `io/textureSettings.ts`) — obraz to nie wszystko, co plik mówi o teksturze. `BoxTextured.glb` ma współrzędne od 0 do 6, bo obraz ma się powtórzyć sześć razy na ścianie, i zapisuje przy teksturze `REPEAT`; `THREE.TextureLoader` domyślnie **przycina do krawędzi**, więc każda współrzędna powyżej 1 pobierała piksel z brzegu i cała bryła wychodziła jednolicie szara — objaw **nie do odróżnienia** od „tekstura się nie wczytała", przez co szukaliśmy jej w geometrii, w shaderze i w R3F. `flipY` z tego samego powodu: glTF wymaga `false`, a przepisanie obrazu na `data:` zachowuje orientację, więc ustawienie musi jechać razem z nim. **Materiał dostaje `key` z listy obecnych map**: obraz dochodzi po pierwszym renderze, a Three kompiluje shader pod zestaw map z chwili powstania materiału — bez odbudowy tekstura nie pojawia się na modelu, bez błędu i bez ostrzeżenia), **`generujUv`** (`geometry/uvProjection.ts`) liczy współrzędne tekstury z kształtu siatki — rzut płaski z wybranej osi albo sześcienny (każdy trójkąt z osi, do której jest najbardziej zwrócony; wynik **bez indeksów**, bo wierzchołek na krawędzi potrzebuje osobnych współrzędnych dla każdej ściany). Powód: modele z generatorów przychodzą z **automatycznym rozwinięciem** — `Meshy_AI…auto-uv.glb` ma 38 552 trójkąty rozcięte na **964 wysepki** w kwadracie 0–1, pod teksturę wypalaną do tego układu; nałożenie na to zwykłego obrazka daje sieczkę i **żadne ustawienie materiału tego nie naprawi**. Rozpoznaje się to po materiale `__meshy_uv_placeholder__` i teksturze 4×4 piksele. `SceneSerializer`/`Deserializer`. **Interfejs jest częścią sceny:** `ui-root` (tryb layoutu + parametry + więzy) i `ui-widget` (panel/button/label/bar) są zwykłymi węzłami, więc hierarchia sceny **jest** hierarchią layoutu, zapis sceny zapisuje interfejs, a zaznaczenie w drzewie jest zaznaczeniem w widoku. Węzły niosą **opis**, nie wynik — pozycje liczy `@mhersztowski/layout` przy każdym rysowaniu (`uiLayout.ts`: `buildUiDoc`/`solveUiLayout`/`applyUiDrag`). Położenie i rozmiar są **tekstem**, bo wolno w nich napisać `parent.w / 2 - 40`; identyfikatorem kształtu w wyrażeniach jest **nazwa węzła** (gdy jednoznaczna i wyglądająca jak identyfikator — inaczej id techniczny i uwaga w `issues`). **Tekstury materiału**: `MaterialDescriptor.texturePath` (ścieżka w VFS — przeżywa zapis sceny) obok `textureDataUrl` (gotowy adres); ścieżkę rozwiązuje host przez `resolveTextureSrc`, tak samo jak dźwięk przez `resolveAudioSrc` — rdzeń nie wie, skąd biorą się pliki. Mapa koloru trafia do **każdego** materiału, który ją obsługuje (basic/lambert/phong/toon/standard/physical) — wcześniej umiał ją tylko `MeshStandardMaterial`, więc ustawienie tekstury na innym typie nie robiło nic bez śladu. W inspektorze `RichEditor`-a pole tekstowe + wybór z plików projektu (`onBrowseTexture`); w cad-app jeden picker obsługuje dźwięk i teksturę — dźwięk dostaje **adres** strumienia (`<audio>` odtwarza wprost), tekstura **ścieżkę VFS** (to ona przeżywa zapis sceny), a dla obrazów okno pokazuje siatkę miniatur zamiast listy nazw. `SimpleViewer` przyjmuje `overlay3d` (treść React w kanwie, poza grafem sceny).
- **ui-core** — hooks, theme, context (no external deps). `defaultTheme` (dark), `ConfigProvider` (CSS custom properties `--mhersztowski-*`), `useDialog`/`useToast`/`useToggle`, generic `deepMerge`.
- **ui-components-scene3d** — `RichEditor` (3-pane Allotment: SceneTree | Viewport | Properties; menu File, toolbar Move/Rotate/Scale), panels (SceneTree/Properties z decoupled inputs/Animation z keyframing/Prefabs), **`UvProjectionControls`** w sekcji Geometry (tylko dla siatek `custom`: tryb płaski/sześcienny, oś, skala, obrót; mówi wprost, że nadpisuje UV z pliku, i pokazuje, czy siatka je w ogóle ma). **Warstwa interfejsu**: `New → UI Layer / UI Panel / UI Button / UI Label / UI Bar` w drzewie, `UiSection` w inspektorze (tryb, parametry na suwakach, więzy z licznikiem stopni swobody, kotwice, `grow`/`basis`, kontener), `UiLayer` renderujący widżety **`@react-three/uikit`** w kanwie (wszystkie `positionType="absolute"` — yoga liczy tylko wyśrodkowanie napisu). Obszarem jest kanwa, więc zwężenie panelu bocznego przelicza układ. Przeciąganie widżetu myszą działa, gdy zaznaczony jest węzeł warstwy; w przepływie odmawia i tłumaczy dlaczego.
- **minislib** — Qt-inspired object system. `Signal<T>`, `MObject` (parent/child tree, tracked connections, `destroy()`), `MProperty<T>`, `MTimer`, `MEventBus`, `MStateMachine`, `MCommand`/`MCommandStack` (undo/redo), `MListModel<T>`, `MLogger`. Publikowany do **GitHub Packages** (workflow trigger: tag `minislib-v*`). W monorepo używaj `workspace:*`.
- **minisc** — kompilator MinisC (C-like → bytecode `.mbc`). Pipeline: lexer→parser→codegen→packer. Runtime to **C++ biblioteka Arduino** (esp32, ~4 KB RAM): stack-based VM wykonujący `.mbc`. Skrypty wgrywane przez MQTT/OTA bez reflashowania. Backend wstrzykuje runtime gdy projekt ma `useMinisC`.
- **core-cad** — CAD 2D/3D core engine (bez renderingu, bez React/Three.js, tylko `crypto.randomUUID`). `EntityRegistry`+typy encji (line/circle/polyline/rect/arc/text/image/freehand/dimension/box3d/cylinder3d/sphere3d), `LayerSystem`, `HistoryManager` (bounded 100), `SelectionManager`, `SnapEngine` (grid/endpoint/midpoint/center/intersection), `EventBus`, `Project` (fasada toJSON/fromJSON).
- **core-cad-viewer** — read-only viewery scen wydzielone z cad-app: `CadViewerPage` (SVG), `Cad3dViewerPage`, `Scene3dViewerPage`, `ElectronicsViewerPage` (lekki SchematicView), `MapViewerPage` (Leaflet), `NotesViewerPage`. Własny minimalny VFS read-client. `setViewerUserId()`. **`scene-api/`** — wspólny sposób mówienia o każdej scenie (`IScene`/`INode`/`INode3D`/`ILayer`/`IEditor`): narzędzia działające na dowolnym trybie (skrypty, agent, szablony, eksport) nie muszą znać `EntityRegistry` ani `SceneGraph`. Adaptery: `Scene3dScene` (drzewo 1:1) i `CadScene` (model płaski → drzewo `root > warstwa > encja`, bo encja i tak nosi `layerId`). Adaptery **nie trzymają własnego stanu** — stąd funkcje pomocnicze zamiast klasy bazowej, która byłaby trzecim miejscem na tę samą informację. `kontrakt.ts` to **jedna suita testów uruchamiana na każdej scenie** (rozjazd między implementacjami wychodzi natychmiast); nie wychodzi z `index.ts`, bo importuje `vitest`.
- **layout** — model układu i **cztery wymienne solvery** na jednym zestawie danych: `static` (wprost z wartości i wyrażeń), `anchor` (kotwice jak w Godocie/Unity), `flow` (jak flex, z `grow`), `constraint` (układ równań jak w szkicu CAD — Gauss-Newton z tłumieniem, jakobian numeryczny, stopnie swobody z rzędu macierzy). Wyrażenia liczy `resolveValues` **pod** solverami, więc `a.x + a.w + margines`, `parent.w` i `viewport.w` działają w każdym trybie; kolejność bierze się z zależności, cykl jest zgłaszany ze wskazaniem pętli. `applyDrag` mówi, co ruch myszą **znaczy** w danym trybie (nowa liczba / zmiana odstępu kotwicy / odmowa w przepływie / nowy stan całego rysunku przy więzach) — dlatego siedzi w pakiecie, a nie w hostach. `snapToGrid` dosuwa **cel przeciągania**, nie rysunek, żeby kształt związany więzem nie skakał za kursorem. Subpath `@mhersztowski/layout/expr` daje sam język wyrażeń (przeniesiony z Rysika). Piaskownica: **Programming → Layout Lab** w mycastle-web (SVG). W edytorze scen warstwa interfejsu jest wbudowana — patrz `core-scene3d` i `ui-components-scene3d`.
- **sci-core** — silnik interaktywnej bazy wiedzy (bez Reacta). Teza: **dokument jest warstwą obliczeniową** — zmiana wzoru w wykładzie zmienia symulację, wyprowadzenie i klucz odpowiedzi zadania naraz. Zjawisko to **graf wzorów (DAG)**, nie jeden wzór z metadanymi. `parseFormula` (bloki ` ```formula ` z `@ode`/`@state`/`@d`/`@init`/`@vars`/`@when`/`@derivedFrom`/`@assume`; **notacją kanoniczną jest LaTeX**), `buildGraph`+`compileGraph` (graf → `PhenomenonModel` jako **artefakt kompilacji**, wyrażenia kompilowane raz przez CortexJS Compute Engine), solvery (rk4/euler/verlet + `Trajectory`), jednostki (`parseQuantity`/`toSI`/`sameDimension`, CODATA — **stała fizyczna wchodzi jako domyślna tylko przy zgodnym wymiarze**, inaczej `\sigma` Lorenza dostałaby stałą Stefana-Boltzmanna), `suggestViews` (dobór widoku z **wymiarów**, nie z nazw), `walkthrough` (wyprowadzenie krok po kroku), zadania (**jeden blok `exercise`, trzy tryby wynikające z treści**: `@answer` — klucz liczy model, dane losuje ziarno (`exerciseVariant`); `@expected` — odpowiedź przepisana z podręcznika, **blok nie liczy nic**, a `statedVariant` wyłuskuje z niej wiodącą wielkość do porównania; brak obu — zadanie jakościowe oceniane samodzielnie. Osobny blok na każdy przypadek dałby setkę bloków i setkę miejsc, w których trzeba pamiętać o powtórkach. `checkNumeric` + `buildHints`; przecinek dziesiętny działa po obu stronach, bo tak pisze uczący się po polsku), `buildIndex`/`search`/`learningOrder` (indeks ze **skanu VFS**, bez osobnej bazy), `worker/protocol` (przez granicę wątku idzie **opis** modelu, nie model), **`pde/grid2d`** (pola na siatce 2D: `@pde` z `@grid`/`@domain`/`@boundary`, schemat jawny różnic skończonych, **krok czasowy dobiera solver** z warunku stabilności, wynik to **klatki**, nie trajektoria; równania liniowe w polu i laplasjanie dostają szybką ścieżkę wykrywaną numerycznie — 6× szybciej), **`progress/schedule`** (powtórki rozłożone w czasie; odstęp zależy od **liczby użytych podpowiedzi**, nie tylko od poprawności), **`linalg/`** (algebra liniowa jako **typy wielkości**: `Matrix2`/`Vector2`, wyznacznik jako zmiana pola, wektory własne ze wzoru zamkniętego, `interpolate` dla animacji od identyczności; blok `@linalg` z `@mat`/`@vec` ma **własny mały ewaluator** — `A \cdot v` zależy od typów operandów, więc silnik numeryczny sprowadziłby wszystko do skalarów; podmiana wartości ma pierwszeństwo nad definicją, żeby dało się animować złożenie; `interaction` — chwytanie wektorów, `alignment` jako miara „jak blisko kierunku własnego", `snapToEigen`; `procedures` — Gauss i Gram-Schmidt zwracają **listę kroków z opisem**, nie wynik, bo treścią lekcji jest droga; **`matrix3`+`compileLinAlg3`** — wymiar wynika z zapisu (`@mat3`/`@vec3`), wartości własne z **równania sześciennego** rozwiązanego wzorem zamkniętym (Cardano/postać trygonometryczna, bez iteracji), `kernelBasis` daje jądro jako prostą albo płaszczyznę), **`validation/`** (cross-walidacja ze SciPy — `latexToPython` tłumaczy z **MathJSON**, nie z zapisu ascii, bo ten zostawia niejawne mnożenia i symbole w cudzysłowach; `exportScenario` dokłada **punkty kontrolne**, żeby rozjazd tłumaczenia wyszedł przed całkowaniem i nie udawał błędu solvera; fixtures regenerowane osobnym poleceniem `node validation/generate-fixtures.mjs <python>`, nigdy w teście — patrz `validation/README.md`), **`formula/editFormula`** (wskazanie i podmiana wzorów w bloku — operuje na **wierszach**, nie na sparsowanym modelu, żeby drobna poprawka nie przepisywała autorowi całego bloku; Jeden klient `{user}/desktop-native/{clientId}` loguje się (`client-login`) i rejestruje trzy wirtualne peryferia jako **devices** przez `client-device-new` (mouse=`vmouse`, keyboard=`vkeyboard`, display=`vdisplay`), każde z toggle enable/disable w UI. Lifecycle na client **outbox**: `client-login`/`client-logout`/`client-device-new`/`client-device-remove`/`heartbeat`. Komendy przychodzą na `{...}/device/{id}/inbox` → `device.handle(type, payload)` → odpowiedź `{type}.ok`/`error` na `{...}/device/{id}/outbox`. `client_desktop_devices.py` — Qt-free logika (mouse/keyboard przez `pynput`, display trzyma stan + callback do UI). `client_desktop_client.py` — `ServerLogicClient` + `ClientSignals` (QObject bridge network→main thread). Tray icon: Show / Quit, close→minimize to tray. Run: `python -m apps.client_desktop` / `run_client_desktop.bat` / `run_client_desktop.sh`. Wymaga działającego `IotServer` (przez `SERVER_LOGIC_AUTOSTART=true` albo skrypt Drive z transportem subskrybującym `#`).

- Run: `app/client/run.sh` (auto venv + deps przy pierwszym uruchomieniu). Win32: osobny venv `.venv-win` (venv jest OS-zależny) — używaj `run_*.bat`.

#### monaco-backend (port **1994**) + monaco-web (dev port **1995**)
Samodzielny edytor kodu — ten sam `TextEditorWorkspace` z `packages/texteditor`, który obsługuje edytor w Drive, ale bez reszty MyCastle.

- **monaco-backend** — cienki serwer na `@mhersztowski/core-backend`. `MonacoHttpServer extends HttpUploadServer` dokłada jedyną brakującą rzecz: kontrakt VFS pod `/api/vfs/*` (`capabilities`/`stat`/`readdir`/`readFile`/`stream` + POST `writeFile`/`delete`/`rename`/`mkdir`/`copy`), dokładnie taki, jakiego oczekuje `RemoteFS`. Własny katalog danych `app/monaco-backend/data` (env `MONACO_DATA_DIR`, ścieżka względna liczona od katalogu aplikacji, nie od `cwd`).
  - **Budowanie Hydry** (`src/hydra/`) — `GET /api/hydra/status` i `POST /api/hydra/build`. To **jedyne miejsce, w którym serwer uruchamia proces**, więc granice są wąskie i sprawdzane czystą funkcją `planHydraBuild` (test `plan.test.ts`): buduje się wyłącznie katalog pliku `.hydra` leżącego **wewnątrz katalogu danych**, a nazwa środowiska musi wyglądać jak nazwa środowiska. `spawn` bez powłoki — katalogi ze spacjami nie wymagają cytowania. Odpowiedź to **`text/event-stream`** (`{type:'line'}` / `{type:'done',code}`), bo budowanie wsadu trwa minuty i bez wierszy na bieżąco nie widać różnicy między „kompiluje" a „zawisło"; `X-Accel-Buffering: no`, inaczej pośrednik zamienia strumień w jedną paczkę na końcu. Rozłączenie klienta ubija kontener (`req.on('close')`).
  - **Katalog Hydry** wskazuje `HYDRA_DIR` (patrz `.env.example`), bo Hydra żyje w osobnym repozytorium (MinisProjects) i nie da się jej wskazać ścieżką wewnątrz tego. Bez zmiennej backend sprawdza `../MinisProjects/libs/Hydra` obok monorepo i `git/MinisProjects/libs/Hydra` w katalogu danych. Brak katalogu **nie blokuje startu** — mówi o tym dopiero panel Kompilacja.
  - **Dwie drogi budowania, wybierane z pliku projektu, nie osobnym przyciskiem.** Cele sprzętowe idą przez `pio run -e <cel>`. Cele natywne (`mcu: native` — okno na maszynie deweloperskiej) **nie mają wpisu w `platformio.ini`**: `emitPlatformio` pomija je świadomie, bo `platform = native` nie obsłuży programu okienkowego z SDL. Idą przez CMake, jako **dwa osobne uruchomienia** (`cmake --preset` + `cmake --build --preset`) — połączenie ich w jedno wymagałoby powłoki, a błąd konfiguracji ma zatrzymać budowę, nie puszczać kompilacji przeciw nieaktualnej pamięci podręcznej. Objawem braku tej ścieżki było `UnknownEnvNamesError: Unknown environment names 'podglad'`.
  - **Preset CMake opisuje maszynę kontenera, nie przeglądarki** — edytor bywa otwarty na Windows, gdy backend siedzi w WSL na ARM. Dlatego `/api/hydra/status` zwraca `arch`, a frontend wylicza z niego preset przez `hostPlatformFor('linux', arch)`; presety mają warunek `hostSystemName == Linux`, więc wariant z przeglądarki kończyłby się odmową cmake.
  - **Trzy drogi celu natywnego, wybierane z systemu przeglądarki** (`targetOs()` w `hydraBuild.ts`) — program natywny jest dla maszyny użytkownika, a nie dla kontenera. Linux: `cmake --preset` + opcjonalne uruchomienie (przycisk „Wgraj" dla celu natywnego znaczy „uruchom tutaj"; w WSL okno SDL trafia na pulpit Windows przez WSLg, dlatego uruchamiamy **poza** kontenerem — inaczej trzeba by przekazywać gniazdo Waylanda). Windows: krosskompilacja mingw, wynik jako **archiwum** (`.exe` + `SDL2.dll`), bo sam plik wykonywalny nie uruchomi się u odbiorcy bez biblioteki. Uruchamianie celu Windows w kontenerze jest wprost odmawiane — program dla Windows nie wystartuje w obrazie, w którym powstał.
  - **Obrazy kontenera:** bazowy `ghcr.io/platform-minis/hydra-build:latest` (publiczny, 13.8 GB, `docker pull` bez logowania) nie ma cmake ani SDL2. Warstwa pochodna `docker/hydra-native/` dokłada cmake, SDL2, `zip` oraz **llvm-mingw** z targetem `aarch64-w64-mingw32` i SDL2 skrosskompilowanym dla Windows ARM64 (`docker build -t mycastle-hydra-native:local docker/hydra-native`). Pochodna zamiast poprawki w Dockerfile Hydry, bo przebudowa bazowego oznaczałaby ponowne ściągnięcie wszystkich toolchainów. Backend wskazuje obraz przez `HYDRA_IMAGE` w `.env`; obraz pochodny jest nadzbiorem, więc obsługuje wszystkie drogi.
  - **Dlaczego llvm-mingw, a nie Visual Studio ani zwykły mingw-w64:** klasyczny mingw-w64 nie ma wariantu `aarch64` (Debian daje tylko x86_64 i i686), a wariant x86_64 działałby na Windows ARM przez emulację — przy podglądzie w czasie rzeczywistym to strata bez powodu. MSVC odpadł praktycznie: toolset ARM64 jest tylko w VS 18, a tamtejszy MSVC 14.50 nie linkuje SDL2 (`_Interlocked*` jako symbole zewnętrzne, tak samo na 2.30.9 i 2.32.8). llvm-mingw to 74 MB pobrania, zachowuje interfejs GCC (`aarch64-w64-mingw32-g++`) i zbudował SDL2 w 30 s. Runtime linkujemy statycznie (`-static`), żeby archiwum miało dwa pliki, a nie pięć.
  - **`SDL_MAIN_HANDLED` zamiast `SDL2main`** (`emit/cmake.ts`): na Windows `SDL2main` podstawia własne `WinMain` i szuka `SDL_main` — symbolu powstającego wyłącznie z `#define main SDL_main` w `<SDL.h>`. Aplikacja Hydry dołącza `Hydra.h`, bo SDL jest szczegółem backendu wyświetlania, więc konsolidacja kończyła się `undefined symbol: SDL_main`. `SdlDisplay` woła w zamian `SDL_SetMainReady()`.
  - **Warstwa hostowa Hydry jest przenośna** (zmiany w repo MinisProjects): `HostFileSystem` operuje na `std::filesystem` z `std::error_code` — `dirent.d_type`, `DT_DIR` i dwuargumentowy `mkdir` nie istnieją w mingw, a `#ifdef _WIN32` dałoby dwie ścieżki do utrzymania. Dodatkowo `M_PI` (rozszerzenie POSIX, nie standard) i `PTHREAD_STACK_MIN` (brak w winpthreads) zastąpione własnymi stałymi.
- **monaco-web** — React 18 + MUI 6 + Vite 6, jedna strona (`EditorPage`) montująca `RemoteFS` na `/api/vfs` w `TextEditorWorkspace`. Bez agenta AI, terminala i `projectDeps` — backend nie ma odpowiadających im tras, a akcje projektowe wymagają nazwy użytkownika, której w aplikacji bez logowania nie ma. `monacoWorkers.ts` skopiowany z cad-app (te same patche na wyścig JSON workera). Buduje się do `../monaco-backend/public`, tak jak cad-app do cad-backendu. **Wtyczka Hydra Studio** wchodzi przez `extraPlugins` — otwarcie pliku `.hydra` z eksploratora pokazuje interfejs projektu obok zakładki tekstowej. `runBuild` (`pages/hydraBuild.ts`) najpierw **generuje `platformio.ini`** z treści **modelu edytora** (a nie z dysku — budujemy to, co widać, łącznie z niezapisanymi zmianami; pliku nie ma w repozytorium, bo powstaje z projektu, a bez niego `pio run` kończy się „Not a PlatformIO project"), potem czyta strumień z `POST /api/hydra/build`. `fetch` + reader zamiast `EventSource`, bo ten drugi umie wyłącznie GET, a żądanie niesie ciało.
- **Porty w jednym miejscu:** `app/monaco-backend/.env` (`MONACO_BACKEND_PORT`, `MONACO_WEB_PORT`) — `vite.config.ts` monaco-web czyta ten sam plik, więc zmiana portu nie wymaga ruszania dwóch konfiguracji.

## Deployment (Coolify)

**Obraz powstaje POZA serwerem — Coolify go tylko pobiera.** Maszyna produkcyjna ma **3,4 GB RAM**, a `vite build` w mycastle-web żąda `--max-old-space-size=8192`, czyli 8 GB heapu. Budowanie na miejscu wchodziło w swap, mieliło **19 minut** i kończyło się zabiciem `node` przez OOM (`load average 74`), kładąc przy okazji panel Coolify — objawem było `exit code 255` bez żadnego komunikatu błędu oraz `502` na UI. `docker-compose.yml` ma więc `image:` zamiast `build:`.

Dwie drogi zbudowania obrazu, obie wypychają `ghcr.io/mhersztowski/mycastle-backend` (`latest` + `sha-<commit>`):
- **`.github/workflows/build-image.yml`** — runner GitHuba, x86_64 natywnie, 16 GB RAM, cache warstw między przebiegami. Odpala się na push do `main` (poza zmianami w `**.md`/`docs/`) albo ręcznie.
- **`scripts/deploy-image.sh`** — z maszyny deweloperskiej. **Uwaga na architekturę:** serwer jest `x86_64`; budowanie na ARM (Apple Silicon, Windows on ARM + WSL) wymaga emulacji QEMU — jednorazowo `docker run --privileged --rm tonistiigi/binfmt --install amd64` — i trwa wielokrotnie dłużej niż natywnie. Skrypt sprawdza obecność emulacji **przed** budową, bo bez niej pierwsze `RUN` kończy się kodem 255 bez wyjaśnienia. Token: `GHCR_TOKEN`/`GITHUB_TOKEN` z `write:packages`.

Zmiana w kodzie wymaga teraz **dwóch kroków**: zbuduj i wypchnij obraz, dopiero potem Redeploy w Coolify. Sam Redeploy podniesie to, co już leży w rejestrze pod `latest`.

**Gotchas Dockerfile'a backendu** (oba objawiły się dopiero na produkcji): `COPY scripts/` musi wejść **przed** `pnpm install`, bo root `package.json` ma hook `postinstall` — bez tego instalacja przerywa się po pobraniu 2051 paczek. Każdy nowy pakiet workspace używany przez `mycastle-web` wymaga **trzech** wpisów: manifestu przed instalacją, źródeł i `RUN pnpm --filter … build` przed budowaniem weba — inaczej `tsc` zgłasza `TS2307: Cannot find module` (tak wyszło z `hydra-studio`). Ta sama lista żyje w skrypcie `build:mycastle` i rozjeżdża się niezależnie.

- `docker-compose.yml` — 2 serwisy: `backend` (1894, volume `/data`) + `web` (nginx :80, proxy do backend).
- Frontend Dockerfile **usuwa `.env` przed buildem** — `urlHelper.ts` auto-detect z `window.location`.
- nginx proxy: `/mqtt` (WebSocket upgrade), `/upload`, `/files/`, `/ocr`, `/webhook/` → backend:1894.
- W Coolify: Docker Compose resource → przypisz domenę do serwisu `web`. `demo-scene-3d` osobny resource.

## Common Gotchas
- **ESM barrels:** Backend `index.ts` musi używać `export type { ... }` dla TS interfaces (ESM type erasure → "does not provide an export named").
- **pnpm strict mode:** wszystkie deps explicit w `package.json` (no hoisting transitive deps).
- **Aedes ESM:** `import aedes from 'aedes'` (default only), then `const { createBroker } = aedes`.
- **WSL vs Windows:** `pnpm install` tworzy OS-specific bin shims. Wszystko z WSL.
- **VITE_* env vars:** baked at build time. Vite ładuje `.env.development`/`.env.production` automatycznie. W produkcji Docker `.env` jest usuwany, URL auto-detect.
- **App singleton (frontend):** używaj `App.instance.serviceName` zamiast bezpośrednich importów. `App.create()` w `main.tsx` przed renderem.
- **MQTT:** unikalne client IDs. WebSocket path `/mqtt`. Shared mode (single port) w deployment.
- **FilesystemContext:** `dataVersion` counter triggers re-renders na FILE_CHANGED events.
- **Zgłoszenia urządzeń:** klient publikuje `minis/{user}/{device}/register-request` (topik w rejestrze Zod; wysyłają `agent.py`, `client_desktop`, `iot-client.module.js` i `IotDeviceClient.requestRegistration()`). Backend trzyma je w tabeli `device_request` (klucz `user_id`+`device_name`, powtórki odświeżają `last_seen_at`), REST: `GET /api/users/{u}/device-requests`, `POST .../{name}/approve` (dopisuje wpis do `Device.json`), `DELETE .../{name}`. Panel z prośbami jest **na górze Electronics → Devices**; samo połączenie z brokerem nie tworzy urządzenia — potrzebna akceptacja.
- **Skrypty przeglądarkowe w Drive:** biblioteka Qt (`qobject.module.js`/`qt.module.js` z `drive/users/{u}/lit/qt`) ładuje się **tylko gdy skrypt jej używa** (`pages/drive/potrzebneQt.ts`). Wcześniej szła twardo przed każdym uruchomieniem, więc brak tych plików w katalogu użytkownika blokował **wszystkie** skrypty — także takie, które tylko czytają scenę — komunikatem „Failed to fetch dynamically imported module", niezwiązanym z treścią skryptu.
- **IoT device key:** zawsze **deviceName** (w MQTT topics, rejestrach backendu, API). SN tylko do śledzenia buildów.
- **MqttClient size-aware:** <2MB przez MQTT, większe przez HTTP. `setUserBasePath(path)` izoluje tenanta.
- **`@react-three/uikit` w cad-app przypięty do 0.8.21:** linia 1.x jest pod `@react-three/fiber` 9 i augmentuje `ThreeElements`, którego fiber 8 nie ma — augmentacja psuje globalną przestrzeń JSX, a objawem jest ~142 błędy `TS7006 implicit any` w handlerach MUI **w plikach niezwiązanych ze zmianą**. Podniesienie wymaga najpierw fibera 9 (i React 19).
- **CAD `useRegisterFileOps` w cad-app:** `register`/`unregister` muszą być stabilnymi triggerami z `useCallback([])` — zależność od obiektu `ctx` powoduje pętlę renderów (bump version → nowy ctx → nowy render).
- **Vite cad-app aliases:** react/emotion + `optimizeDeps.exclude` workspace paczek — zapobiega wielokrotnym instancjom React z `node_modules`.
